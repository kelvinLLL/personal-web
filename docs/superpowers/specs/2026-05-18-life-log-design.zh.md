# Life Log 设计说明（中文 Review 版）

## 目标

为 `personal-web` 增加一个独立的私人生活札记频道：`Life Log`。

这个频道用于记录语音转写后的个人感悟、日常事件、探索生活的片段，以及那些如果不立刻保存下来就会从时间里溜走的想法。它首先是一个私人记忆档案，其次才是一个未来可能被整理成作品或书稿的内容库。

第一版不直接嵌进现有前端，而是在 `personal-web` 根目录下新建独立工作区：

```text
/Users/haojunliu/Easy/NapPlace/personal-web/life-log/
```

这个工作区先负责数据格式、生成流程、解析逻辑和可选预览。等内容格式和使用习惯稳定后，再集成到个人网站主前端。

## 产品定位

`Life Log` 是独立频道，不混入 `Daily Nuance`。

它不是 AI 日报，也不是知识管理系统。它更像一个私人书桌上的生活札记盒子：每天可以往里面放一张纸，未来再回头看自己是如何变化的。

核心体验是：

> 我可以回来看看，当时的我正在变成什么样的人。

## 第一版用户流程

第一版写入流程不放在网页里，而是通过 Codex 完成：

1. 用户使用任意外部工具完成语音转文字。
2. 用户把转写文本发给 Codex。
3. Codex 根据固定结构生成当天的 Life Log Markdown 文件。
4. 如果用户后续补充内容，Codex 可以继续修改当天这篇。
5. `life-log/` 工作区解析这些 Markdown 文件，并生成可被预览或未来网站集成消费的数据。
6. 之后再把 Life Log 集成进 `personal-web` 的主前端导航与页面。

这个设计故意不在第一版做网页编辑器、在线语音识别、在线 AI 改写、数据库保存和鉴权流程。第一版要证明的是：记录习惯和内容结构真的有用。

## 数据目录

Life Log 第一版的数据放在：

```text
life-log/data/entries/
```

普通情况下一天一篇：

```text
life-log/data/entries/2026-05-17.md
```

如果一天有多篇，可以加短后缀：

```text
life-log/data/entries/2026-05-17-wedding.md
```

后续如果需要给前端消费，可以生成：

```text
life-log/generated/
```

比如：

```text
life-log/generated/entries.json
```

## 单篇记录格式

每篇 Life Log 是一个 Markdown 文件，前面带 frontmatter：

```md
---
date: 2026-05-17
title: 婚礼、正反馈和一块拼图
mood: 感慨
source: voice-transcript
visibility: private
tags:
  - 婚礼
  - 探索生活
  - 正反馈
  - 小世界与大世界
---

## 今日发生的事

- 去参加了贝贝和他老婆的婚礼。

## 今日核心感悟

...

## 整理版

...

## 札记版

...

## 原始记录

...
```

## 内容结构

每篇记录都应包含这些部分：

- `title`
  - 具体、可记忆，不要太泛。
  - 例如：`婚礼、正反馈和一块拼图`。
- `date`
  - 使用 Asia/Shanghai 本地日期。
- `mood`
  - 一句短情绪，例如：`感慨`、`松动`、`开心`、`有点孤独`。
- `tags`
  - 用于未来检索和重组，例如：`探索生活`、`婚礼`、`日剧`、`小世界与大世界`。
- `今日发生的事`
  - 事实和事件 bullet，不做太多文学化处理。
- `今日核心感悟`
  - 这一天真正值得留下的心理变化或问题。
- `整理版`
  - 把原始流水账整理成清晰、有层次、但仍然像用户自己的表达。
- `札记版`
  - 可以稍微文学化，但不能写成泛泛的鸡汤或陌生人的美文。
- `原始记录`
  - 保留语音转写原文，作为源材料。

原始记录不是噪音，它是证据。后面的整理版和札记版可以不断变化，但原始记录应该保留下来。

## 写作原则

Codex 生成 Life Log 时要遵守：

- 保留用户自己的思考节奏。
- 不要把表达洗成通用 AI 美文。
- 不要过度拔高。
- 可以整理，但不能替用户假装已经想明白了。
- 对尚未确定的问题，要保留“不确定”的状态。
- 多抓具体画面，而不是只写抽象道理。

例如 2026-05-17 的婚礼记录，真正的核心不是“参加婚礼”，而是：

- 看到朋友进入人生下一个阶段；
- 自己在热闹场合里没有被主动搭话；
- 由此思考自己是不是仍需要他人的正反馈；
- 从乐高小人想到未来婚礼拼图；
- 把“人与人如何拼出一个人生”这个意象保存下来。

## 前端方向

第一版不直接做完整个人网站集成，但设计要为未来集成预留。

未来网站中的 Life Log 可以有两个页面：

### Life Log Index

按时间倒序展示所有记录：

- 日期
- 标题
- mood
- tags
- 一小段摘要

它应该像一个安静的私人档案，不像社交 feed。

### Life Log Entry

单篇详情页展示：

- 标题
- 日期
- tags
- 今日发生的事
- 今日核心感悟
- 整理版
- 札记版
- 原始记录折叠区

原始记录默认可以折叠，不要一打开就占据主要阅读空间。

## UI 气质

这个频道不需要营销感、英雄区、装饰性大图，也不需要像博客首页一样强调发布。

推荐气质：

- 安静
- 私密
- 适合长文本阅读
- 像私人书房或笔记册
- 信息密度适中
- 标签弱化，不喧宾夺主

核心是让用户愿意回看，而不是让别人觉得页面很炫。

## 第一版实现范围

第一版实现建议只做：

- 创建 `life-log/` 根目录工作区。
- 创建 `life-log/data/entries/`。
- 放入至少一篇样例记录，例如 2026-05-17 婚礼札记。
- 写解析逻辑，读取 Markdown + frontmatter。
- 生成 `life-log/generated/entries.json` 或类似快照。
- 如果需要，做一个最小预览页验证内容展示。
- 加测试，确保 Markdown 能被正确解析。

第一版不做：

- 在线录音
- 语音转文字
- 网页内 AI 改写
- 网页编辑器
- 数据库
- 多用户鉴权
- 评论
- 对外发布流程

## 后续阶段

后续可以逐步加入：

- 集成进 `personal-web` 主前端导航。
- Life Log 列表页和详情页。
- 标签筛选。
- 搜索。
- 月度/年度回顾。
- 标记“可公开”或“只私密”。
- 轻量编辑标题、标签、mood。
- 按主题生成书稿章节，例如：
  - 第一次
  - 小世界与大世界
  - 和陌生人
  - 允许自己开心
  - 人生节点

## 关键决策

### 为什么选 Markdown

因为 Life Log 的核心是写作和记忆，不是结构化数据库。

Markdown 的好处：

- 人可以直接读。
- 方便长期保存。
- 适合未来整理成文章或书。
- frontmatter 足够承载日期、标题、标签等结构化信息。

### 为什么先不做网页编辑

因为第一版真正要验证的是：

- 用户是否愿意持续记录；
- Codex 是否能稳定整理成可读札记；
- Markdown 格式是否足够舒服；
- 回看是否有价值。

网页编辑器可以之后再加。太早做编辑器会把注意力从“记录生活”转移到“造 CMS”。

### 为什么先独立 `life-log/`

用户明确希望先新开一个根目录下的文件夹，未来再集成到个人网站。

这样做的好处：

- 不污染现有前端结构。
- 数据格式可以先稳定。
- 生成工作流可以独立测试。
- 未来集成时只消费稳定产物。

## 测试要求

实现时至少要测试：

- Markdown frontmatter 必填字段解析。
- 缺少可选字段时不会崩。
- 样例 entry 能生成 snapshot。
- 生成的 snapshot 能被预览或未来前端消费。

## 当前推荐

按这个路径推进：

1. 先实现 `personal-web/life-log/` 独立工作区。
2. 用 2026-05-17 婚礼札记作为第一篇样例。
3. 生成 `entries.json` snapshot。
4. 做一个很小的本地预览。
5. 等确认内容结构舒服后，再接入 `personal-web` 主前端。
